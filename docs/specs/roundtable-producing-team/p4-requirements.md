## Requirements

**RR-1 — Role assignment provenance: append-only events on the thread, durable service ledger off-TTL**
Roles live only in skill prose today (PACK-6); rotation needs code-level provenance. Two stores, matching what actually needs to survive. (1) **Per-thread provenance events**: the moderator (R1: moderator owns all I/O) writes an append-only event stream on the producing thread — a `scheduled-assignment` event at thread open (`{run_id, spec_subject, assignments: {seat: role}, basis: fixed|rotation, created_at}`), and later events appended on discovery (`fallback`, `seat-lost`) rather than mutating the original. This resolves the round-2 immutability-vs-discovery conflict: records are never edited, only extended. (2) **Durable rotation ledger**: because board threads TTL at 7 days (PACK-3), the ledger of drafter service — the input to RR-2's pointer — lives in a TTL-exempt ledger namespace, a `board.py` extension with a defined record shape (`{run_id, spec_subject, owed_seat, actual_drafter, served: bool}`). The round-2 board backfill of the two fixed-role threads is withdrawn (it contradicted write-at-open and the threads TTL anyway); instead the fixed-role history is recorded as structured lines in decisions.md (tracked, durable, chair-owned), which RR-4 consumes.

- No seat is briefed on a producing thread before the `scheduled-assignment` event exists; violation is detectable by ordering of board writes, and a test asserts the moderator refuses to brief without it.
- Provenance events are append-only: a test attempts in-place mutation through the board API and asserts rejection; fallback is representable only as a new event naming the displaced seat.
- The rotation ledger survives thread TTL: a test expires a producing thread and asserts RR-2's pointer function still computes from the ledger alone.
- `board.py` API additions (write event, read event stream, append ledger record, read ledger) are named in the design phase; RR-1 is not satisfied by prose conventions over free-text messages.
(table: agreed; chair: approved)

**RR-2 — Rotation algorithm: owed-pointer semantics, atomic reservation, idempotent runs**
Round 2 shipped two contradictory rules (seat-after-previous-drafter vs deferred-turn). Resolved — one algorithm, stated fully. The ledger tracks one **owed seat**. Rule: *the pointer advances past a seat only when that seat has actually served as drafter* (served = delivered the Round-1 draft that passed `lint_draft`, with or without its one repair). Formally, over the canonical seat order (the `SEAT_RECIPES` order: claude, antigravity, codex): if the most recent ledger record has `owed_seat == actual_drafter` and `served == true`, next owed = seat after `owed_seat` in canonical order; otherwise next owed = `owed_seat` unchanged. Substitute service (RR-3) never advances the pointer — so if A is owed and absent, B substitutes, and A is owed again next spec; when A serves, the pointer moves to B, who may thus draft twice in three specs. That asymmetry is accepted: it is deterministic, pure over the ledger, and preserves "deferred, not consumed" without a second rule. Concurrency and idempotency (round-2 gap): appending an assignment record is an atomic compare-and-set against the ledger head; run identity is a stable `run_id` (`producing-<spec-slug>-<slot>`); a second append with a duplicate `run_id`, or a new run for a spec subject with an active thread, is rejected and receipted as `DUPLICATE_RUN` (RR-7) with zero rotation consumption. A retried failed run does not double-consume a turn, because the pointer only ever advances on recorded *served* drafts.

- A pure-function test replays ledgers containing absences, substitutions, and failed runs and asserts the assignment sequence, including the A-absent/B-substitutes/A-owed-next case that round 2 left undefined.
- Two concurrent run attempts for the same slot: exactly one wins the CAS; the loser posts a `DUPLICATE_RUN` receipt and makes no ledger, thread, or candidate writes.
- Critic roles are derived (the two non-drafter seats) but named explicitly in the RR-1 event; role-aware budgets (`ROLE_REPLY_CHARS`, PACK-4) are resolved by recorded role, never by seat name.
(table: agreed; chair: approved)

**RR-3 — Absence: discovered by invocation failure, fallback at open, typed terminal mid-round; quorum floor needs the chair**
There is no separate availability probe: absence is discovered exactly as the shipped runner discovers it — an invocation that fails (nonzero exit, timeout, missing binary), and failed attempts count against R5 (honest accounting, no free probes). **At thread open** (first drafter invocation fails): the next seat in canonical order substitutes as drafter, a `fallback` event is appended (RR-1), and per RR-2 the pointer does not advance — the absent seat is owed next. **Mid-round** (round-2 gap, both critics): no mid-thread reassignment ever. A critic failing mid-round after one retry degrades per R6 — its critique is recorded `MISSING` in the objection ledger and the run continues. The drafter failing after Round 1 (so no revision/final is possible) is a typed terminal: the run ends `SEAT_ABSENT`, completed rounds are preserved on the thread, and **no candidates are staged** (there is no `lint_final`-clean output to stage — this is the two-outcome model of RR-5, not a third path). **Quorum**: my recommended floor — a run with zero available critics does not stage candidates, because an uncritiqued draft entering the chair's queue as tidy candidates is the exact rubber-stamping trainer PACK-6 names. Codex correctly objects that this makes an absence block a run, colliding with binding R6 ("absent seat never blocks; table degrades"). Both readings are defensible; neither seat can waive an invariant. Until the chair rules, the R6-compliant behavior ships as default: the run proceeds, and its output is staged with an `UNCRITIQUED` degraded status flagged at digest-header and per-item level (RR-7). The abort alternative is on the table for the chair.

- Drafter absent at open with two seats remaining: run proceeds with substituted drafter + one critic; the substitution and single-critic condition both appear in the digest header, and the `MISSING` critique is explicit in the objection ledger, never inferable-only.
- Drafter lost after Round 1: run terminates `SEAT_ABSENT` with rounds preserved and zero candidates staged; a test induces a mid-round drafter failure and asserts the terminal, the receipt, and the empty candidate set.
- Zero critics available: run completes and stages `UNCRITIQUED`-flagged candidates (default pending chair ruling); a test asserts the flag is present on every staged item, not only the header.
(table: contested — zero-critic production: R6's letter vs the trust-machine risk; chair must rule (codex raised, drafter agrees it is chair territory; chair: approved)

**RR-4 — Rotation trigger: attested baseline evidence, machine-checked; chair-armed activation**
"Once the loop is baselined" gets criteria under TR-9 discipline — shipped artifacts, never process volume — while fixing round 2's computability gap (no machine-readable receipt existed for "survived downstream execution", and board TTL killed board threads as evidence). Resolution: human judgment supplies the facts; the machine checks *recorded attestations* in a tracked file. Eligibility inputs are structured lines in `docs/specs/roundtable-producing-team/decisions.md`, written by the chair (or moderator at the chair's direction) during normal ruling flow: `P4-BASELINE: thread=<id> promoted=<item-ids> downstream=<PR/commit ref or pending>`. Eligibility = at least **two** distinct `P4-BASELINE` lines (two completed fixed-role spec-loops with per-item promotions actually exercised through TR-2), of which at least **one** carries a non-pending `downstream` ref (the promoted artifact was cited and used by real implementation work — the chair attests this; the machine only parses it). Activation is never automatic: rotation turns on only with an arming line (`P4-ROTATION: armed <date>`), a chair ruling like every other mode change in this spec. `rotation_status` reports `not_eligible` / `eligible_unarmed` / `armed`, always with the specific evidence lines.

- `rotation_status` is computable from decisions.md alone (tracked, durable — no dependence on TTL'd board threads); a test runs it against fixture files covering all three states and malformed lines (malformed = reported, never guessed).
- No count of rounds, invocations, critiques, or agreement rate appears anywhere in the eligibility computation (TR-9 guard, assertable in review).
- Until the arming line exists, every thread's RR-1 event has `basis: fixed` with the PACK-1 fixed assignment; the first `basis: rotation` event cites the arming line.
(table: agreed; chair: approved)

**RR-5 — Producing routine: input contract, explicit state machine, lint gates, binding budget default**
`run_routine` supports one flat-capped round plus synthesis (PACK-6); producing mode is a **distinct spec type**, not a mutation of clean-run. **Input contract** (round-2 MISSING, both critics): `ProducingRoutineSpec` carries the spec subject, a grounding-pack source (path or board-thread ref), the `run_id` scheme, and check names; a scheduled run with an empty, unreadable, malformed, or already-consumed grounding pack terminates `INPUT_INVALID` before any seat is briefed (no invocations spent on garbage). **State machine** — D3's 3-round ceiling maps to exactly three structural rounds, and lint repairs are intra-round (they count against R5 only, never D3 — absorbing both critics' objection that repairs would eat the ceiling): Round 1 = drafter briefed (grounding pack; `drafter` budget) → `lint_draft`; Round 2 = each critic briefed (pack ref + the full lint-clean draft; `critic` budget) → `lint_critique` per reply; Round 3 = drafter briefed (draft + both critiques verbatim, or `MISSING` markers per RR-3) and produces the tagged final document itself — the moderator runs lints and assembles but never authors content (R1) — → `lint_final`. Each gated reply earns exactly one re-brief carrying the lint output; dirty-after-repair is recorded and terminates per RR-7 (`LINT_DIRTY`) — un-linted or dirty text never reaches the compiler. **Compile semantics** (codex #5, absorbed): `compile_requirements` honors per-item chair rulings, and a headless run has none — so a headless run produces an **unruled candidate compilation**, every item honestly recorded unruled per PACK-4, and is never presented as final assembly. Final assembly is a post-run moderator step re-running the compiler over the chair's recorded per-item rulings (RR-6). **Budget arithmetic** (codex #6): happy path = 4 LLM invocations (1 draft + 2 critiques + 1 final); worst case adds 4 repairs (one per gated reply) = 8; failed absence-discovery attempts also count (RR-3); deterministic lints and compile count zero. Proposed **binding default `max_invocations = 10`** (8 + 2 discovery margin), shipped as the implementation default and submitted for chair ratification in decisions.md — resolving round 2's open question rather than deferring it. R5 halt behavior is unchanged: cap reached → halt posted naming the round in progress, all completed rounds preserved.

- A full headless run on a prepared pack yields either a lint-clean unruled candidate compilation staged per RR-6 or a typed RR-7 terminal — a test enumerates the state machine's terminals and asserts no other exit exists.
- D3 accounting: a run with all four repairs used still completes all three structural rounds; a test asserts repairs never trigger `ROUND_CEILING`.
- Per-invocation accounting (seat, role, round, repair flag, failed-attempt flag) is recorded on the thread; a test drives the run to the cap and asserts the halt post and preserved partial state.
- `INPUT_INVALID` fires before any seat invocation on each malformed-input class (empty, unreadable, malformed, already-consumed), asserted per class.
(table: 2-1 — codex holds the R5 cap must be chair-ratified before the requirement is implementable; drafter and the moderator's contract accept a proposed binding default ratified through normal flow; chair: approved)

**RR-6 — Staging: R8 absolute, 7 per session (not per spec), single-writer recomposition, one thread per run**
R8 is absolute: the routine never promotes; output waits on the board for the chair. **Thread scheme** (antigravity #8, absorbed): one producing run = one board thread, `producing-<spec-slug>-<run-id>`, carrying the RR-1 events, all rounds, the staged candidates, and the digest as its head message — the chair navigates from digest to candidates by item id within a single thread, deterministically. Each parsed requirement is staged as an individually promotable candidate (per-item promotion is the ruled model, PACK-1). **TR-6 correction** (antigravity #1, absorbed — round 2's wording implied over-cap items were unreachable): TR-6 = 7 caps candidates *per session*, not per spec. A compilation exceeding 7 stages the first 7 in document order; the remainder are held on the thread as `deferred_over_cap` — full text preserved, honestly counted in the digest header — and become stageable in a **subsequent chair-initiated session** (the chair asks; the routine never auto-splits or auto-restages). No item is ever silently dropped or permanently stranded. **Recomposition** (codex #11, absorbed): the shared requirements document is produced only by the moderator — sole materializer (PACK-1) — re-running `compile_requirements` over the chair's recorded per-item rulings (deterministic assembly; declined/unruled ids recorded honestly per PACK-4), materialized via P3 `materialize` into a detached scratch worktree for `diff_against_base` chair review. Single writer + deterministic assembly = no conflicting writes by construction. Per TR-2, scratch worktrees and the board are the only pre-approval homes; promotion to a tracked path is per-item, chair-only, through the board's promote path.

- A grep/test over the producing-routine code path asserts zero calls into promote; after a headless run, the board shows staged candidates with zero promotions attributable to the routine.
- A synthetic 9-item compile stages exactly 7 and holds 2 `deferred_over_cap` with full recoverable text; a follow-up chair-initiated staging of the remainder succeeds without re-running any seat.
- Recomposition over a ruling set (some approved, one declined, one deferred) yields a deterministic document with declined/unruled ids recorded; running it twice byte-matches.
- No tracked path is written by a producing run under any outcome, including failure, halt, and `UNCRITIQUED`; materialized artifacts are scratch-only and `discard`-idempotent.
(table: agreed; chair: approved)

**RR-7 — Failure honesty: a closed taxonomy, typed receipts, out-of-band path for board loss, dissent-first digest**
Headless runs have no human to notice degradation, so the machinery confesses it (TR-9; TAC-4 spirit: failed-with-receipts or withheld, never laundered). Round 2's "closed but at minimum" contradiction is fixed: the taxonomy is **closed at v1** — `INPUT_INVALID`, `PRECHECK_FAILED` (keyless checks / preflight), `DUPLICATE_RUN`, `SEAT_ABSENT` (seat, role, round, substitution status), `UNCRITIQUED` (degraded status per RR-3 default), `LINT_DIRTY` (round, seat, literal lint output after the one repair), `ROUND_CEILING`, `BUDGET_EXHAUSTED`, `COMPILE_ERROR`, `MATERIALIZE_FAILED`, `BOARD_WRITE_FAILED`, `BOARD_UNREACHABLE` — adding a code requires a spec amendment, so unclassifiable conditions surface as implementation bugs, not quiet new categories. **Receipts** (codex #13, absorbed): P3's `CheckReceipt` is not overloaded — a distinct `FailureReceipt` shape carries `{code, run_id, thread_id?, round?, seat?, role?, structured detail, evidence}` where `evidence` is a verbatim tail (capped at 2,000 chars) only for conditions that have subprocess/lint output; conditions without output carry structured fields, not fabricated tails. Seat invocations already run provider-clean (PACK-3); the evidence cap bounds stored provider output. **Board-unreachable** (codex #1, absorbed): a digest cannot be posted through a dead board — the shipped runner probes reachability first; on failure it writes an out-of-band local failure receipt (the routine's log location, the same surface launchd already captures) and exits nonzero, and the requirement states plainly that this one class cannot appear on the board. **Digest discipline**: every run that touches the board posts a digest whose header enumerates all conditions that occurred — failures first, then the dissent register / contested items per `lint_final` tagging, then agreed candidates (the inverse of the tidy-queue ordering PACK-6 names as the rubber-stamping trainer). A degraded run's digest is structurally distinct from a clean run's, and degradation flags appear per-item where the promotion decision happens. A scheduled run that produced nothing still posts a failure digest; an empty board after a scheduled slot is itself a bug.

- Each taxonomy code is inducible in a test harness; the induced run's digest (or out-of-band receipt for `BOARD_UNREACHABLE`) names the code, and the receipt's structured fields match the schema.
- `LINT_DIRTY` receipts contain the literal lint output; receipts for output-less conditions (e.g. `DUPLICATE_RUN`) contain no `evidence` field; both asserted.
- A test renders digests for a clean run and each degraded variant and asserts the header shapes differ and failures precede candidates in all cases.
(table: agreed; chair: approved)

## Non-goals

- **Rotating the moderator or the chair.** The moderator remains sole materializer and I/O owner (R1, PACK-1); the chair remains sole promoter. Only member-seat roles rotate.
- **Auto-promotion in any form**, including "promote if lint-clean and no dissent." R8 and "no auto-promotion ever" are untouched; RR-4 stops at reporting eligibility, RR-6 stops at staging.
- **Changing ruled or shipped constants**: D3 = 3, TR-6 = 7, `ROLE_REPLY_CHARS`, thread TTL for deliberation threads, and the clean-run routine's behavior and schedule are inputs, not outputs. (The TTL-exempt ledger namespace of RR-1 is new state, not a change to thread TTL.)
- **Mid-thread role reassignment.** Absence mid-thread produces degradation or a typed terminal (RR-3), never a role swap.
- **New scheduling infrastructure.** Producing routines use the existing launchd-style arming pattern from P3.
- **Multi-spec batching in one scheduled run.** One run = one spec subject = one candidate session. Pipelining multiplies staged candidates against the chair-attention budget.
- **Chair-attention analytics or rubber-stamping detection.** The trust-machine risk is mitigated structurally (RR-7 ordering, degraded and `UNCRITIQUED` flags); measuring chair behavior is explicitly not built.
- **Automated downstream-citation tracking.** RR-4 deliberately uses chair-attested structured lines, not a citation-mining index; building one is out of scope.
