Pick up the decision, not just the conversation

When you return, establish what the report should do, what actually happened and whether anything needs action.

Open the supplied formatted report. Its useful result is easy to recognize: six synthetic entries account for 270 minutes, with totals by project and category.

Imagine returning tomorrow. “Continue” could mean finishing a draft, inspecting a completed result or handling a concern. Those actions have different effects.

Ask your assistant to locate the actual saved reporting task and inspect it before proposing more work. The report file alone cannot establish which task produced it, what checks ran or what a reviewer found.

Ask for a read-only inspection

Use the saved path from your earlier work. If it is missing, locate it before running a task command.

  1. Find the actual task directory retained by the earlier workflow.
  2. Have the assistant confirm its identity, goal and current state.
  3. Read the accepted scope, recorded execution, checks, findings and next action together.
  4. Keep missing evidence visible. Successful inspection does not mean the work is complete.
Optional CLI reference: inspect saved status

Use the selected installed Harness environment. Replace the entire absolute path with an existing saved task directory; do not paste the placeholder unchanged.

attune-harness status /absolute/path/to/saved-reporting-task --format markdown

status reads the saved task. It does not dispatch a participant or continue execution. If the path is refused or no record exists, inspect the error and locate the original task. Do not invent a replacement record.

If you have no saved task of your own, use the supplied current check summary for the evidence exercise. Treat that summary as a reference, not as an active task in your project.

A saved task is completed and its chosen checks passed. What should your return brief say?

State which checks passed, inspect remaining findings and retain the limits of that evidence. A completed workflow and passing selected checks are useful evidence. They do not erase findings or establish untested behavior.

State that all possible report behavior is correct, because completed means no further concern is possible. Completed describes the recorded workflow. Read its checks, findings and limits before deciding whether any further action is needed.

stopping-note prompt

Prepare a short stopping note for the actual reporting task we just inspected. Use its verified task identity and revision. State the goal, where we stopped, evidence locations, unresolved concerns and the next decision with its reason. Distinguish recorded Harness results from work performed outside that task. Preserve prior notes, and show me this new note before saving it. Do not revise accepted scope or resume execution.

Notice when the next step changes scope

Suppose you return and now want the report to show only Orion. That is a requirement to inspect, not just a reminder.

First establish whether the current tool already supports that selection. If it does not, describe project filtering as a proposed change. Preserve the original all-project report and its existing checks.

Ask for a separate change brief or the supported task-revision route. Changing a stopping note does not change accepted scope. Reopening a briefing does not authorize execution, and an old checkpoint is not approval for a changed requirement.

Explain which next action is justified: read the existing project total, review a concern, prepare a new scoped change or stop. You do not need a new build when the current report already answers the question.

Return with a decision you can explain

You can now say what the work was for, which evidence you inspected and why the next action is warranted.

  • Name the actual task or supplied evidence you inspected.
  • Distinguish a saved draft, accepted scope and recorded execution.
  • Explain one result and one remaining limit.
  • Choose inspection, review, a proposed scoped change or no further work.

For this course, the next useful action is to assess the report's evidence. You do not need another build to read what the current result supports.
