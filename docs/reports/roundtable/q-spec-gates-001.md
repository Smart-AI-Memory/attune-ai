## #1 — question (chair)

Where can the round-table team improve or create processes for spec-driven development — specifically intelligent progress/quality gates insertable into the spec lifecycle (brainstorm → requirements → design → tasks → execution → verification) that can run either autonomously or with human review/approval? List concrete opportunities, each with: the gate's trigger point, what it checks, its autonomous vs. chair-gated mode split, and what it builds on that exists in attune today (compiler lints TR-4, producing runs V2-P4, RR-1-style readiness gates, drift-guard tests, the curator sources surface, delegation receipts, the decisions.md chair-ruling convention).


## #2 — position (claude)

POSITION: Gates should be cheap mechanical refusals at every phase boundary, with the chair ruling only on promotion and anything irreversible. Autonomous mode may BLOCK AND REPORT, never APPROVE AND ADVANCE. Six gates: (1) Premise-validation gate (brainstorm->requirements): grep every named scope item against the tree, refuse authoring below 100% resolution with exact deltas (mechanizes the "spec text goes stale, code is the contract" lesson; corpus-readiness shape). (2) Falsifiability lint on requirements: every acceptance criterion carries a named receipt type + a probe that would fail if false; "configured/registered/exits-0" phrasings are lint errors; chair rules on receipt-type adequacy. (3) Symbol-reality gate on design: every referenced API/class/flag resolves (import it, --help it) — fully autonomous, with a [[?slug]] escape hatch for not-yet-built symbols (doc-import-gate ported). (4) Headless task authoring under producing-run caps: tasks pass XML-prompt schema lint + requirement-trace lint (orphan tasks and undischarged requirements block); promotion always human. (5) Central receipt re-run at execution exit: orchestrator re-runs every lane's declared receipt (suite serial, metric full-stream); live-fire/evidence-chain always chair-ruled. (6) Spec self-truthing sweep (continuous): status fields vs git/gh/PyPI reality; stale specs surface as curator candidates; only a decisions.md ruling closes/re-scopes.
RISK: Ceremony creep and gate-gaming — mechanically-lintable formats get optimized AS formats (Goodhart on gates 2/4); if gates fire on sub-spec-tier work, people route around /spec entirely, which is worse than no gates. Mitigations: tier switch bypassing the ladder for inline/one-shot work; gate 5's central re-run catches gamed claims.
FOLLOW-UP: Should autonomous gate verdicts (pass/block + evidence) be written into decisions.md alongside chair rulings, or kept in a separate machine ledger — protect decisions.md as human-judgment-only, or make it the unified gate history?


## #3 — position (agy)

POSITION: Quality gates must act as deterministic filters with explicit human escalation policies — autonomous checks evaluate structural completeness, static safety, and receipt coverage; chair rulings reserved for architectural trade-offs, scope boundaries, and non-deterministic risk. Five gates: (1) Ambiguity & Assumption Scan (brainstorm->requirements): scan for unstated dependencies/vague criteria; verify referenced symbols exist; auto-pass when references resolve + schema lints pass; ambiguous scope queues to the Curator for chair ruling. (2) Verification Receipt Contract (requirements->design): every requirement maps 1:1 to a named receipt type + failing pre-implementation probe; auto-fail on missing mapping; chair approves live-fire/metric receipts touching external infra. (3) Architectural Blast-Radius & Drift (design->tasks): evaluate proposed interfaces against drift-guard state; auto-pass additive isolated changes; chair-halt on public API/shared schema/security-primitive changes. (4) Cold-Handoff Task Decomposition (tasks->execution): tasks self-contained, non-overlapping file scopes, bounded by invocation caps; auto-approve pure-leaf tasks; chair for structural layout changes, new third-party deps, multi-agent coordination. (5) Non-Mocked Boundary Verification (execution->verification): prove integration seams were tested via real round-trips not mocks; autonomous suite/lint/receipt-log verification; chair gives final promotion approval in decisions.md.
RISK: Gate-induced latency and decision fatigue — thresholds too low make the chair a bottleneck in decisions.md; too relaxed and mock-heavy implementations leak into verification.
FOLLOW-UP: When a live-fire/metric receipt fails on a transient/flaky environment result, may the chair override the gate failure directly in decisions.md, or should overrides always require a spec revision reclassifying the receipt type?


## #4 — position (codex)

POSITION: Six composable gates; each emits evidence + a proposed disposition, but only humans approve scope changes, unresolved tradeoffs, irreversible designs, or acceptance-criteria waivers. (1) Intent & scope gate (brainstorm->requirements): problem statement, target user, measurable outcome, non-goals, constraints, "done when" all explicit; detects solution-first framing; autonomous may flag/request another round within cap or recommend "not ready"; chair approves scope, non-goals, deferred ambiguity. (2) Requirement quality & traceability (requirements->design): atomic, testable, uniquely identified, prioritized, outcome-linked; finds duplicates/conflicts/unverifiable language; mechanical defects auto-repaired and rechecked; chair rules on priority conflicts, deletions, interpretation, accepted gaps. (3) Design fitness (design->tasks): requirement->design-element mapping, tradeoffs recorded, seams/migrations/security/rollback/observability addressed; detects needless parallel mechanisms; chair approves irreversible choices, public API changes, migrations, security exceptions, complexity increases. (4) Executability & verification-planning (tasks->execution): dependency-ordered, independently completable, scoped tasks tracing to requirements; every acceptance claim names its receipt + a probe that would fail if false; system may split oversized tasks and auto-pass fully mechanical plans; chair approves scope reductions, deferred tests, mock-only validation at external seams, destructive-risk tasks. (5) Execution checkpoint & drift (during execution): implementation matches approved design; files within declared scope; projections synchronized; formatting/linting/projection-regen/bounded reruns proceed automatically; chair rules on behavior/criteria/architecture/dependency/scope changes. (6) Acceptance & promotion (execution->verification->completion): requirement-to-change-to-evidence matrix; receipts exist and passed; mocked vs real-boundary distinguished; residual risks listed; system may declare "verification complete" mechanically but NEVER auto-promotes; chair owns acceptance, waivers, promotion. A SHARED GATE PROTOCOL makes these insertable: structured inputs, machine-readable findings, exact shortfalls, evidence references, proposed disposition, and one of four states — PASS, REVISE, CHAIR_REQUIRED, BLOCKED — so each phase doesn't invent its own approval semantics.
RISK: Ceremony inflation — gates optimize documents for internal consistency while slowing small changes and creating false confidence. Mitigation: risk-tiered activation — lightweight mechanical gates for reversible work; deeper chair-gated checks only for ambiguity, external seams, migrations, security, irreversible decisions.
FOLLOW-UP: Should gate policy be fixed per lifecycle stage, or selected dynamically from a spec's risk profile while preserving a small mandatory baseline?


## #5 — synthesis (moderator)

SYNTHESIS (moderator, round 1 — halting on convergence, D3):
AGREEMENT (strong, all three seats):
- Gate placement: all seats put gates at the same five lifecycle boundaries (brainstorm->requirements, requirements->design, design->tasks, tasks->execution, execution->verification), plus continuous/drift monitoring (claude #6, codex #5).
- The autonomy split is unanimous and crisp: autonomous gates may BLOCK/REPORT/FLAG with evidence and exact shortfalls, but only the chair may APPROVE scope, irreversible choices, waivers, and promotion. Never-auto-promote generalizes to never-auto-advance-on-judgment.
- Receipt-first verification: all three make "every acceptance claim names its receipt type + a probe that would fail if false" a mechanical lint (claude gate 2, antigravity gate 2, codex gate 4), with mock-vs-real-boundary distinction enforced at execution exit (all three).
- Reality-grounding: all three want spec text validated against the live tree (claude premise-validation + symbol-reality; antigravity symbol-existence scan; codex parallel-mechanism detection).
- The named RISK is the same word in two seats: ceremony inflation (codex, claude "ceremony creep"), decision fatigue (antigravity) — and the mitigation converges on RISK-TIERED ACTIVATION: a small mandatory baseline for all work, the full ladder only for spec-tier/irreversible work.
DISTINCT CONTRIBUTIONS:
- codex: the SHARED GATE PROTOCOL — one machine-readable finding format with four states (PASS / REVISE / CHAIR_REQUIRED / BLOCKED) so every phase shares approval semantics. Strongest single structural idea on the table.
- claude: gates mapped 1:1 onto SHIPPED attune mechanisms (compiler-lint seam, corpus-readiness shape, doc-import-gate port, producing caps, central receipt re-run, curator self-truthing sweep) — the cheapest build path.
- antigravity: blast-radius classification (additive/isolated auto-passes; public API/schema/security always chair) — the cleanest autonomous-vs-chair decision rule.
MODERATOR READ: the three positions compose rather than conflict — codex's protocol as the container, claude's mechanism mapping as the implementation path, antigravity's blast-radius rule as the escalation policy, risk-tiering as the guard against the shared failure mode.
OPEN FOLLOW-UPS FOR THE CHAIR (R9): (a) gate verdicts in decisions.md vs a separate machine ledger [claude]; (b) chair override of flaky live-fire receipt failures directly vs via spec revision [antigravity]; (c) fixed per-stage gate policy vs risk-profile-dynamic with mandatory baseline [codex].
