## Phase 1 — Engine telemetry hooks (no UI, no daemon)

Goal: add the per-source event-sink plumbing to the discovery-sweep
engine. Pure Python, no daemon dependency. Lets us validate the
hook shape in isolation before wiring it up.

- [ ] **1.1** Add an `EventSink` type alias (`Callable[[dict[str,
      Any]], Awaitable[None]]`) and threaded `event_sink: EventSink
      | None` kwarg through `DiscoverySweepWorkflow.execute()` →
      `_run_source()`.
- [ ] **1.2** Add a `sweep_id: str | None` kwarg, generated by
      callers (daemon supplies; CLI leaves None). Engine
      doesn't generate it.
- [ ] **1.3** Implement `source_started` / `source_finished` /
      `source_failed` event emission inside `_run_source`. Use
      `asyncio.create_task(event_sink(event))` rather than
      `await event_sink(...)` so a slow sink doesn't block.
- [ ] **1.4** Add a `_iso_now()` helper that produces
      `datetime.now(timezone.utc).isoformat()` and re-use it for
      all event timestamps.
- [ ] **1.5** Tests in `test_event_sink.py`:
      - `event_sink=None` is a no-op (today's behavior preserved)
      - Event sink fires exactly once per source per outcome
        (`started` + (`finished` xor `failed`))
      - Event shape matches the dataclass spec in `design.md`
      - A sink that raises doesn't propagate into the sweep
      - A sink that's slow doesn't block other sources' execution
- [ ] **1.6** CHANGELOG entry under `### Added`.

## Phase 2 — Daemon HTTP / SSE plumbing

Goal: wire the engine's event sink to the ops-runner-tier2 daemon's
SSE stream so the dashboard can subscribe.

- [ ] **2.1** Add `POST /workflows/discovery-sweep/run` endpoint
      to the daemon. Body: `{path, depth?, no_llm?, source?,
      verbose?}`. Returns `{sweep_id}` immediately; sweep runs in
      a background task.
- [ ] **2.2** Wire the daemon's per-sweep `event_sink` to push
      events onto the existing SSE stream (`GET /events` from
      ops-runner-tier2).
- [ ] **2.3** Implement atomic write of `<scope-hash>.json` +
      `<scope-hash>.meta.json` to `~/.attune/ops/sweep-results/`
      when the sweep completes.
- [ ] **2.4** Add `GET /workflows/discovery-sweep/results/<hash>`
      that returns the latest sweep JSON for that scope, or
      `404` if no sweep has run yet.
- [ ] **2.5** Tests in `tests/integration/ops/test_sweep_via_dashboard.py`:
      - Trigger sweep via HTTP, assert SSE events arrive in order
      - Assert JSON file lands at the expected path
      - Concurrent sweeps on different scopes don't clobber each
        other's storage

## Phase 3 — Dashboard UI

Goal: render the discovery-sweep row + chips + live progress +
drill-in in the workflows.html dashboard page.

- [ ] **3.1** Discovery-sweep row honors the existing scope picker
      (already supported via `PATH_ARG_REGISTRY` from parent spec
      P1.7 — verify rendering only).
- [ ] **3.2** Per-bucket colored chips on each row (queue / questions
      / rejected). Empty buckets render as `0`, not hidden.
- [ ] **3.3** Live progress bar while a sweep runs — reads SSE
      events and renders `✓ pattern-scan ⏳ bug-predict ⌛ security-audit`
      style sequential status.
- [ ] **3.4** Chip click navigates to detail view with the bucket
      filtered (`?bucket=queue` / `?bucket=questions` / `?bucket=rejected`).
- [ ] **3.5** Detail view renders findings via the generic
      finding-row component. Includes severity badges (same
      Phase 3.2 color tokens), file:line link, evidence
      collapsed by default.
- [ ] **3.6** Tests:
      - `test_workflow_list_chips.py` — chip count loader
        (missing file → zeros, corrupt file → zeros + warning)
      - Smoke test via Playwright (or whatever ops-runner-tier2
        uses for UI testing) — chips render, click navigates,
        detail page loads.

## Definition of done

- All four phases shipped on `main`
- Dashboard renders discovery-sweep with chips + live progress
- Detail view works with the existing run-view component
- Manual smoke test on at least one real repo (run a sweep, see
  the chips update live, click through to a finding)
- This spec is marked DONE in `_sequencing.md`

## Out of scope (post-spec follow-ups)

- Multi-repo aggregation
- Slack / GitHub PR comment integrations
- Trend dashboards / time-series storage
- Auth / multi-user (inherited from ops-runner-tier2 single-user
  assumption)
- Re-run-from-dashboard button — deferred to a v2 if user demand
  exists; v1 is read-only after the CLI / cron triggers the
  sweep.
