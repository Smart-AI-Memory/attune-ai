Turn a concern into a checkable question

A plausible concern deserves a concrete input and expected result before you decide whether it is a defect.

Illustrative concern: a missing row

Suppose a report omitted the final 15-minute Orion testing entry. This is a proposed counterexample for learning, not an observed finding in the current software.

  1. Identify the exact input: the unchanged six-row CSV.
  2. State the independent expectation: 6 entries, 270 minutes and Orion at 180.
  3. Describe the supposed failure: 5 entries, 255 minutes and Orion at 165.
  4. Ask whether current output or a suitable test actually shows that mismatch. Keep the concern unconfirmed until the evidence exists.

If a mismatch is observed, retain the failing input/output and choose a bounded investigation or correction. If it is not observed, report that outcome. A suggestion does not become a bug because it sounds reasonable.

Handle a real finding without changing the answer

When evidence establishes a defect, preserve the expectation and make the correction inspectable.

Use the missing-row concern as a paper exercise. Decide what a repair task would need before authorizing it:

  1. Keep the six-row input and independently derived expected totals.
  2. Prepare a focused check that exposes an observed mismatch. Verify it against the failing behavior before treating it as a regression check.
  3. Define the smallest allowed implementation change and protect the acceptance expectation from the repair worker.
  4. After separately authorized work, inspect the same check, actual diff and broader relevant results. Preserve failed attempts and any remaining concerns.

Notice when a plausible total is wrong

The omitted-row example lets you practice checking a result with fewer hints.

If the final 15-minute testing row were omitted, the report would show 5 entries and 255 minutes. Orion would total 165 and Testing 30; Lumen would remain at 90. These numbers could look plausible until compared with the complete input.

  1. Identify the omitted row in the six-row fixture.
  2. Recalculate one affected subtotal.
  3. Explain which check would expose the omission: entry count, grand total, project total or category total.
  4. State what your check would leave untested, such as invalid input or output-file handling.

Use an independent expected answer. Asking the same implementation to produce its own expected total can repeat the same mistake.
