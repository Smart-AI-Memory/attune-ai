# Requirements — Discovery Sweep

**Status:** approved with notes

User-facing stories and the contracts they imply. See `decisions.md` for context, `design.md` for the technical shape, `tasks.md` for the phase plan.

---

## Personas

- **Pat (project owner)** — runs the sweep against his own code daily. Wants a triaged queue, not prose. Will read `questions` but won't read `rejected`.
- **Casey (contributor)** — runs the sweep against a PR's diff scope to decide whether to approve. Wants to know in 30 seconds whether anything in `queue` looks scary.
- **CI (automation)** — runs the sweep on `main` post-merge and surfaces `queue` count to a dashboard. Treats `questions` as soft signal, not blocking.

---

## User stories

### US-1 — One command, every audit lens, triaged output

**As Pat, when I want to know "what's worth looking at across the code I just changed," I want a single command that runs every relevant audit and hands me back a triaged queue.**

```bash
attune workflow run discovery-sweep --path src/attune/security/
```

Acceptance:

- One invocation fans out to all default sources (1 pattern + N LLM)
- Total wall-clock time is bounded by the slowest source, not the sum (sources run in parallel where possible — see design.md)
- Output prints three sections: `## Queue (N findings)`, `## Questions (M findings)`, `## Rejected (K findings, --verbose to see)`
- Each `queue` finding renders as a clickable file:line link
- Exit code is 0 if `queue` is empty, 1 if `queue` is non-empty (CI-friendly)

### US-2 — Budget is a hard ceiling, not a suggestion

**As Pat, when I pass `--budget 3.00`, I want the sweep to spend at most $3.00 across all LLM sources combined and stop cleanly if it would exceed that.**

Acceptance:

- Per-source budget is `budget_usd / len(llm_sources)` by default
- Pattern source consumes $0 (regex, no LLM)
- A source that hits its allocated budget mid-discovery returns whatever findings it has so far + a `questions` entry noting partial completion
- Total spend reported in the output footer: `Spent: $X.XX / $Y.YY budget`
- If `--budget` is omitted, default is $10.00 (see decisions.md DECIDE callout)

### US-3 — Questions bucket is actionable, not advisory

**As Pat, when a finding lands in `questions`, I want enough context to decide whether it's a real issue without re-running anything.**

Acceptance:

- Each question entry includes: the finding text, which source raised it, why the engine routed it to `questions` (e.g. "no location given", "conflicting severity from bug-predict vs security-audit", "novel pattern"), and a one-line "next step" hint
- The hint is generated by the verification rules at routing time, not by an LLM (cost discipline)
- Questions never have severity higher than their underlying finding — they don't escalate

### US-4 — Verbose output exposes the rejected bucket for rule debugging

**As Pat, when the sweep returns an empty `queue` but I think it shouldn't, I want to see what got rejected and why.**

```bash
attune workflow run discovery-sweep --path X --verbose
```

Acceptance:

- Default output omits the rejected bucket entirely (just shows count in the footer)
- `--verbose` renders each rejected finding with its source, severity, and the verification rule that rejected it
- Rejection reasons are enumerated constants (`SEVERITY_BELOW_THRESHOLD`, `DUPLICATE_OF`, `LOCATION_MISSING_AND_PATTERN_MATCHED`, etc.), not free text — so users learn the rules over time

### US-5 — JSON output for CI / dashboard integration

**As CI, when I run the sweep post-merge, I want machine-readable output so I can render queue counts and trend them over time.**

```bash
attune workflow run discovery-sweep --path . --json
```

Acceptance:

- Top-level shape: `{ "queue": [...], "questions": [...], "rejected": [...], "metadata": { "spent_usd": ..., "budget_usd": ..., "sources": [...], "duration_ms": ... } }`
- Each finding has a stable schema (see design.md for the dataclass shape)
- The metadata block is sufficient for cost trending without parsing the findings

### US-6 — Surface evaluation is reproducible

**As Pat, when I want to know whether any standalone audit CLI can be deprecated in favor of the sweep, I want a documented procedure I can re-run when sources change.**

Acceptance:

- A script or documented procedure runs both the sweep and each underlying workflow standalone on the same path
- Findings are cross-referenced — every standalone-workflow finding must map to one or more sweep findings (queue OR questions, not rejected)
- Output is a markdown table per workflow with DEPRECATE CLI / KEEP CLI / DEFER recommendations
- Lives in `docs/specs/discovery-sweep/surface-evaluation.md` (see P2.7)

## Non-functional requirements

### NFR-1 — Sources isolate failures

If one source crashes (network error, parse failure, SDK timeout), the sweep continues with the remaining sources. The failed source contributes a single `questions` entry: "Source `X` failed: <error>. Re-run individually to investigate."

### NFR-2 — Pattern source is offline-capable

`PatternScanSource` works without `ANTHROPIC_API_KEY` set. It's the floor of the sweep — even with no LLM access, the user gets pattern-detected findings. Drives the `--no-llm` flag in the CLI (excludes all LLM sources, runs pattern source only).

### NFR-3 — Output is reproducible at fixed path + SHA

Running the sweep twice on the same `--path` at the same git SHA should produce queues with the same finding count and the same set of file:line entries. (LLM-generated text within a finding may vary; the *set* of findings should be stable.) This is aspirational for v1 — we don't enforce it via tests yet.

### NFR-4 — Engine is LLM-free

The verification rules and triage routing are deterministic code, not an LLM call. This keeps the engine cheap, fast, and testable. (Sources do LLM work internally; the engine doesn't.)
