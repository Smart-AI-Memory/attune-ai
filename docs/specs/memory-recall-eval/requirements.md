## Problem

`attune.memory` (in particular `PersonalMemory`, the class behind the
`personal_memory_capture`/`personal_memory_recall` MCP tools) is
architecturally mature but was found nearly unused in a live session
(2026-07-01): `personal_memory_topics` returned a single
`dispatch_test` entry. We have **zero evidence** that write-then-recall
actually round-trips correctly for realistic curated-memory content —
not "does it scale," not "is it better than grep," just: if you
`capture()` N facts and then `query()` for them, do you get the right
ones back? That's the prerequisite question before either surface
comparison (harness auto-memory vs. attune.memory) or scale testing
make sense.

## Goal

Build a small, ground-truthed recall-accuracy benchmark against
`PersonalMemory`: capture a corpus of realistic entries with known
facts, run natural-language queries with known expected answers,
measure hit rate, and produce one written verdict.

## Approach

1. **Corpus (isolated, not real memory dirs).** Write N (~15-20)
   synthetic-but-realistic `PersonalMemory.capture()` entries into a
   `tmp_path`-scoped global root — varied `kind`s (`decision`,
   `pattern`, `troubleshooting`, `reference`), varied topics, each
   containing one or two clearly-stated facts (e.g. "the timeout for
   X is 30 seconds," "we chose Redis over Postgres because Y").
   Content should look like real captured memory, not `"test entry
   {i}"` filler — realistic content is what will actually stress the
   RAG pipeline's ranking.
2. **Ground truth.** For each corpus entry, write 1-2 natural-language
   queries a person would plausibly ask to retrieve that fact,
   annotated with the expected topic slug(s). Include a few queries
   with NO good match in the corpus, to check the system doesn't force
   a confident-looking wrong answer (a false-positive check, not just
   recall).
3. **Run the benchmark.** For each query, call `PersonalMemory.query(query,
   k=3)` and check whether the expected topic appears in the top-k
   results. Compute: hit@1, hit@3, and false-positive rate on the
   no-match queries.
4. **Report + verdict.** Write results to `decisions.md`: the numbers,
   2-3 concrete example failures (query + what came back instead) if
   any, and a verdict — good enough as-is / needs tuning / needs
   deeper investigation.

## Requirements

- **R1 — Isolated corpus, not production memory.** The benchmark must
  never write into `~/.attune/personal_memory` or this project's real
  `.attune/memory/` — use `PersonalMemory(global_root=tmp_path, ...)`
  or equivalent isolation. Never pollute real memory with synthetic
  test entries.
- **R2 — Realistic content, not filler.** Corpus entries must read
  like genuine captured memory (a real decision, a real pattern) —
  filler text like `"fact number {i}"` would not exercise the RAG
  pipeline's actual ranking behavior and would produce a meaningless
  number.
- **R3 — Ground truth is hand-authored, not generated by the same
  process being tested.** Query→expected-topic pairs are written by a
  human/agent reading the corpus, not derived mechanically from it
  (avoids circular validation).
- **R4 — Include negative queries.** At least 3-5 queries with no good
  match in the corpus, to catch false-positive over-confidence, not
  just recall misses.
- **R5 — One clean report.** Results land in this spec's
  `decisions.md` as a single dated entry: the numbers, example
  failures, and a verdict. Not scattered across test output.
- **R6 — Cheap to run, not durable infrastructure (v1).** A script or
  a single pytest-marked benchmark test is enough. Don't build a
  re-runnable longitudinal harness unless the first result's verdict
  says it's worth tracking over time (that becomes its own follow-up).

## Non-goals

- Not testing `MemoryGraph`/`add_finding` recall (`find_related`,
  `find_similar`) — that's a different mechanism (graph traversal, not
  RAG retrieval) and a separate future experiment if this one's
  results warrant it.
- Not a harness-auto-memory vs. attune.memory comparison — that's the
  bigger "unify the two systems" question; this spec only evaluates
  attune.memory in isolation.
- Not adding Redis/AMS to run this — the file-backed `DirectoryCorpus`
  is sufficient and matches how `PersonalMemory` is actually configured
  today (Redis untouched per the motivation memory's deferral).
- Not fixing whatever the benchmark finds — a poor result is itself a
  valid, useful outcome (it tells us where to invest). Any fix is a
  follow-up, scoped separately once we know what's broken.

## Done when

- A benchmark corpus + ground-truth query set exists (script or test
  fixture) and is isolated from real memory.
- The benchmark has been run at least once against the current
  `PersonalMemory` implementation.
- `decisions.md` has one dated entry with hit@1/hit@3/false-positive
  numbers, concrete failure examples (if any), and a keep/tune/
  investigate verdict.
