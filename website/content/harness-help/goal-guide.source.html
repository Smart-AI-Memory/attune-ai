# Local activity reporting app — initial spec v0.1

Status: host-authored initial draft for review. No roundtable has reviewed it; no implementation is approved.

## Outcome and scope

Let a person inspect, filter and export synthetic project activity through a small local command-line app. Use BRIEF.md for the product boundary and CSV-CONTRACT-NOTES.md for the established selection and file contract. The fixture's identity rules simulate access; they are not a production security system.

## Workflow

1. Select a simulated user and optionally project, kind, inclusive date range and summary search.
2. List the selected visible activity in stable order.
3. Export the same selection to a new CSV file.
4. Inspect the produced file and review retained check results before accepting implementation.

## Requirements

- R1: Validate the local input schema before presenting or exporting rows. Reject unknown users, duplicate IDs, invalid references, dates, types, negative minutes and disallowed control characters.
- R2: Apply the existing membership and row-restriction rules identically to list and export. Never include membership or restriction metadata as public report columns.
- R3: Intersect all active filters with the exact matching and inclusive date semantics in the existing contract; reject reversed date ranges.
- R4: Order selected rows by ascending date and activity ID without a hidden result limit.
- R5: Produce the seven ordered columns and CSV encoding, quoting, escaping and record endings specified in the existing contract. Preserve Unicode and multiline text through a CSV parser.
- R6: Apply the exact formula-text transformation to every text column in exports, keep minutes numeric and preserve literal text in list output. Make the transformation and importer limitations visible in user guidance.
- R7: Emit only headers for an empty visible selection, refuse overwrites, validate before creating output, clean up a partial new file after a write failure, and keep the fixture unchanged.
- R8: The same source, user and filters must produce identical CSV bytes. Expose the public exported row count without mixing diagnostics into CSV content.

## Acceptance checks

- AC1 (R1): Invalid fixture variants fail before an export file exists; unknown identity fails closed.
- AC2 (R2, R3): Independently assert selection parity and exclusions for memberships, null/named/empty restrictions, each filter and intersecting filters.
- AC3 (R3, R4): Exercise both date boundaries, a reversed range, Unicode-casefold summary search and order after changing input row order.
- AC4 (R5): Parse actual CLI-generated files and inspect bytes for exact columns, UTF-8/no BOM, quoting, escaped quotes, CRLF records and embedded line endings.
- AC5 (R6): Cover the named formula markers, fullwidth forms, leading whitespace/format characters and initial TAB/CR/LF in every text column; verify unchanged literal list output and typed minutes.
- AC6 (R7): Assert the exact header-only empty file, no overwrite, no file on invalid input and cleanup after an injected write failure.
- AC7 (R8): Compare repeated export bytes, source hashes and the separately reported public row count.
- AC8 (R2–R6): Use viewer/atlas/review/2026-10-11..2026-10-12 as a concrete two-row example; manually inspect Unicode, multiline and transformed text in the intended spreadsheet, recording the application/version and import settings. Do not generalize that check to every importer.

## Proposed task dependencies

- T1: Confirm the contract and fixture shape; prepare independent selection, CSV-byte and failure-case acceptance checks. Human settles any material changes to the contract first.
- T2, after T1: Implement shared validation and selection, then list and export behavior using standard-library runtime dependencies. Preserve the independent checks.
- T3, after T2: Execute the agreed checks, retain output and file evidence, write user guidance and conduct the bounded manual spreadsheet check.
